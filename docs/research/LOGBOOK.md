# 研究日誌（實車開發）

專題：多感測器融合感知與智慧決策系統（WRO 2026 Future Engineers）。
這份日誌記錄實車開發的過程、數據、遇到的問題和學到的東西，之後寫專題報告時直接引用。

**寫法**：一次工作一筆，最新的放最上面。每筆盡量包含：

- **目的**：這次要解決什麼
- **做法**：做了什麼（指令細節放 [RUNBOOK](../real/RUNBOOK.md)，這裡寫重點）
- **結果**：有數字就寫數字，附資料位置
- **問題與判斷**：卡在哪、為什麼這樣決定
- **學到**：觀念、原理、教訓
- **下一步**

大型資料（rosbag、CSV、照片）不放進 repo，記下它在哪台電腦的哪個路徑。

- **學到**：Allan variance 一次看出兩種誤差：短時間的白雜訊（ARW，決定 covariance）和長時間的偏差變化（決定要不要 ZUPT / 估偏差）。gyro 偏差每 10 分鐘會變，所以「開機校正一次」不夠，ZUPT 是必要的

## 2026-10-20（凌晨）　步驟 8.2：EKF 第一次上車；加入零速更新（ZUPT）

- **目的**：確認 `localization.launch.py` 在 Orin 上能跑、TF 只有一個發布者、靜止時不會飄。
- **做法**：`orin_check.sh --ekf`（Claude Code 自動執行，只讀），**開機後立刻測**；Windows `下載\r550_check\20261020_031653\`
- **結果**：
  - 通過：`publish_odom_tf` False；`/tf` 發布者只有 `robot_state_publisher` 和 `ekf_filter_node`；`/odom` 19.99、`/imu/data` 20.02、`/scan` 10.04 Hz；TF 0.130, 0, 0.115；靜止 60 秒位置變化 0 m；電池 11.55 V
  - 未達標 1：`/odometry/filtered` **20.1 Hz**（間隔 0.033 / 0.067 s 交替），不是設定的 30 Hz
  - 未達標 2：靜止 60 秒 yaw 0.634° → 1.243°（**+0.61°/min**，標準 < 0.5°），比 10-19 晚上（開機很久後）的 0.25°/min 大
- **問題與判斷**：
  - 1：robot_localization 預設只在有新量測時才往前算並發布，量測是 20 Hz，所以輸出也是 20 Hz。加 `predict_to_current_time: true`，每一輪都預測到現在的時間再發布 → 30 Hz，TF 也比較新
  - 2：韌體只在開機第 10 秒取一個樣本當零點，剛開機時板子溫度在變，偏差跟著變。EKF 的 yaw 只用 gyro，所以偏差直接變成角度飄移
  - **解法：零速更新（ZUPT，Claude Code 建議）**：阿克曼車後輪不轉就不可能轉向（不能原地轉），所以**後輪靜止超過 1 秒時，gyro 讀到的就是偏差**；用時間常數 5 秒的低通濾波一直更新，從 `/imu/data` 扣掉。每次停車都會自動重新歸零，也能跟上溫度變化
  - 防呆：手拿著車轉（輪子不動但車身在轉）時，跟目前偏差差超過 0.01 rad/s 的樣本不用；偏差最大 0.02 rad/s
- **學到**：把「車子的運動限制」（阿克曼不能原地轉）當成額外的資訊來修正感測器，是融合的常見技巧（ZUPT 原本用在行人導航：腳踩地時速度為 0）
- **下一步**：部署後再跑一次 `orin_check.sh --ekf`（開機後立刻測，才看得出 ZUPT 的效果）

## 2026-10-19（深夜）　步驟 7-1：IMU 靜止校正

- **目的**：量 gyro 偏差和雜訊，確認 `imu_link` 朝向，給 EKF 用。
- **做法**：`orin_calib.sh static` 跑 60 秒和 300 秒（Claude Code 自動執行，只讀），Windows `下載\r550_calib\20261019_230938_static\`、`20261019_231057_static\`
- **結果**：
  - IMU 20.0 Hz（只有啟動時斷一次 0.33 s）；重力在 **+z、9.772** → `imu_link` z 朝上，和 URDF 假設一致
  - gyro z 偏差 +0.00007～+0.00009 rad/s（**每分鐘飄 0.24～0.29°**），5 分鐘內逐分鐘 0.07～0.47°/min，穩定
  - gyro x / y 偏差 −0.0022 / +0.0018 rad/s，比 z 大約 25 倍（2D 只用 z，不影響）
  - 雜訊：gyro std 約 0.00037 rad/s（約 1.4 個量化刻度，1 刻度 0.000266 rad/s），variance 1.2～1.7e-7；accel std 約 0.005 m/s²，variance 約 4e-5
  - 靜止時 odom 0 m、0°
  - 光達 USB 沒插，`scan_node` 找不到序列埠就結束，不影響這次
- **問題與判斷**：
  - 讀韌體原始碼：開機第 10 秒把 gyro **三軸**和 accel 都各取**一個樣本**當零點（不是只歸零 z）。所以偏差大小看開機那一瞬間：只取一個樣本、沒有平均，x / y 比較大可能是開機後溫度變化或那一刻剛好偏，原因 UNKNOWN
  - accel 也被歸零（z 再加 1 g），所以 accel x / y 永遠以「開機時的姿勢」為水平，−0.026 / +0.033 **不是**真正的傾斜，不能拿來量
  - covariance 改成 gyro 1e-6、accel 1e-4（比靜止實測大幾倍，留給行駛時的震動）
  - EKF 方向：`two_d_mode`；IMU 只融合 vyaw（accel 不用）；odom 先融合 vx，vyaw 等 `wz_scale` 驗證後再決定；EKF 發 `odom → base_link` 時，`publish_odom_tf` 改 false
- **學到**：感測器「出廠校正」做了什麼要看原始碼；雜訊用 variance（std 的平方）填進 covariance，而且要比靜止時大，因為行駛時有震動
- **下一步**：手推直走（`vx_scale`）、手推左彎（`wz_scale`、gyro 正負號）

## 2026-10-19　指令端第一次架空測試；後輪 2 顆馬達確認

- **目的**：第一次讓馬達轉，驗證 `base_node` 的速度換算和 `/cmd_vel` 逾時停車。
- **做法**：車子架空、Motor ON，`base.launch.py enable_commands:=true max_vx:=0.1`，發 0.1 m/s 約 5 秒後停止發布。由 Ray 電腦上的 Claude Code 執行，結果在 Windows `下載\r550_airtest\20261019_163853_v01x5\`
- **結果**：
  - 送出 103 個指令封包（約 5.2 秒）；後輪穩定時 `/odom` 平均 **0.100 m/s**（0.094–0.103）
  - 起步：0.7 秒到 0.095 m/s
  - 停車：停止發布後 **0.3 秒逾時**，輪速再 **0.8 秒**降到 0，沒有倒轉；總共約 1.1 秒
  - 只有後輪轉：**馬達只有 2 顆，在後輪（MotorA/B），C/D 沒接**；前輪靠舵機轉向、不出力
- **問題與判斷**：
  - 0.8 秒是 STM32 的 PI 控制慢慢減速，不是立刻煞停；在地上有摩擦應該更快，要地面再量
  - `/odom` 0.100 和指令用同一個 `vx_scale` 換算，只證明前後一致；真實速度要地面量距離
  - **STM32 韌體沒有指令逾時**（`balance.c` 裡的判斷被註解掉）：node 當掉時車子會照最後的指令一直跑。所以 node 的逾時是唯一的軟體停車，Motor 開關是唯一的硬體停車

- **問題與判斷**：
  - 約 18 % 的點距離是 **0** 而不是文件寫的 `0xFFFF`，也代表沒有回波，driver 改成兩種都忽略
  - 一圈約 533 點、每點 0.68°，原本切 720 格（0.5°）會有 40 % 空格，改成 **480 格（0.75°）**

## 2026-10-16（傍晚）　ROS 第一次看到車子；里程計比例實測

- **目的**：讓 `/odom`、`/imu/data`、`/battery` 出現在 ROS 裡，並確認輪式里程計準不準。
- **做法**：啟動只讀的 `r550_feedback` node（Motor OFF）。車子架空，用手轉後輪：先 1 圈，再 5 圈（減少數圈的誤差），看 `/odom` 的位置。用繩子量輪胎周長。
- **結果**：
  - `/odom` **20.000 Hz**，間隔標準差 0.6 ms；`/battery` 11.67 V；`/imu/data` 加速度 z 9.81
  - 往前轉，x 為正、往右偏時 y 和 yaw 都是負的：**方向符合 REP-103**
  - 5 圈：odom 走了 1.32 m，**每圈 26.4 cm**；實際輪胎周長 **21.5 cm** → STM32 **高估約 23%**，校正係數 21.5 / 26.4 = **0.814**
  - 左右手轉的量不同時 yaw 會變：**STM32 是用左右後輪的速度差算角速度**
- **問題與判斷**：
  - 第一次只轉 1 圈得到 31 cm，其實是數圈不準；改轉 5 圈，數錯半圈的誤差就從 50% 降到 10%

  - 之前說的輪徑 7 cm 不準，周長換算是 6.8 cm
- **學到**：
  - ROS 訊息的 `header`（時間戳記、`frame_id`）、量不到填 NaN、`orientation_covariance[0] = -1` 代表沒有姿態
  - 四元數換角度：`yaw = 2 × atan2(z, w)`
  - 正運動學反推：yaw 偏 −8° 代表左輪多走了 `0.162 × 0.143 ≈ 2.3 cm`
  - 實驗設計：重複多次（轉 5 圈）降低人為誤差

## 2026-10-16（下午）　第一次和 R550 的 STM32 通訊（只聽）

- **目的**：確認 Orin 讀得到 STM32 的回授，而且封包格式和官方文件一樣。
- **做法**：Motor OFF；Windows `git pull` → `scp` 到 Orin → `colcon build`；車上的「STM32通信线」（C30D 上印 `UART3` 的孔）接 Orin；跑 `listen` 10 秒，原始資料存 Orin `~/r550_first.bin`。
- **結果**：
  - USB 轉串口晶片是 **CH9102**（`1a86:55d4`），Linux 內建 driver，裝置 `/dev/ttyACM0`
  - **10 秒收到 4801 bytes，約 20 Hz，壞幀 0**：協定和官方文件一致，`wro2026_base_r550` 在實車上驗證通過
  - 靜止時：vx = wz = 0；加速度 (−0.03, 0.00, 9.81) m/s²；陀螺儀 z 只在 ±0.0005 rad/s（約 ±0.03°/s）之間跳。**WAVE ROVER 的 IMU 靜止標準差是 5.1°/s**，這顆 ICM20948 安靜得多
  - 電池 10.96 V，接近 10.8 V 的建議充電線
- **問題與判斷**：
  - **USB 反向供電**：車子電源關著就插 USB，Orin USB 的 5 V 讓 STM32 開機，但量到的電池電壓接近 0，蜂鳴器每秒響（低電壓警報）。正確順序：車子電源 → 等 10 秒 → 插 USB
  - **舊 build 殘留**：第一次 `ros2 run` 出現 `StopIteration`，因為 Orin 上 10/13 build 的舊版登記資料還在。刪掉這個 package 的 `build/`、`install/` 重新 build 就好
  - **flag_stop 不是 Motor 開關**：開關在 OFF，讀到的 flag 還是 0。`listen` 原本把它顯示成「motor=ON」，會誤導，已改成只顯示數值。安全上**不能用這個值判斷馬達會不會動**
- **學到**：
  - USB 同時帶電源和資料；Linux 用 `/dev/serial/by-id/` 給裝置固定名字
  - 新舊版本混在一起（原始碼或 build 產物）會出怪問題，所以要先清乾淨
  - 文件寫的意義要用實物驗證（flag_stop）
- **下一步**：充電；啟動 ROS node 看 `/odom`、`/imu/data`；Motor OFF 手推車子看 `/odom`。

  - B2：**沒有安裝**。模擬安裝發現 `nav2-bringup` 會把 Ubuntu 的 OpenCV 4.6 開發套件換成 NVIDIA 的 4.8（移除 10 個套件）
  - B3：寫了 R550 序列協定 module（UNVERIFIED）；光達 driver 因為缺套件 build 失敗
  - B4：Foxglove 改成唯讀（不能從介面發指令）；WSL 在 NAT 模式下看不到 Orin 的 topic
  - B5：pose-free 控制器 merge 進來，topic 名稱參數化，修改前後的模擬結果逐字相同
- **學到**：
  - **apt 的優先權**：同一個套件在不同來源有不同版本時，apt 依優先權選。NVIDIA 的來源優先權 600 高於 Ubuntu 的 500，所以會把 OpenCV 換掉。裝之前先用 `apt-get -s` 模擬，可以提早發現這種衝突
  - **DDS 和 NAT**：ROS 2 靠 DDS 的多播自動發現彼此，WSL 的 NAT 網路擋住多播，所以看不到 Orin。改用 Foxglove（WebSocket）可以避開

## 2026-10-13　整理 AI 寫的 repo、建立實車 package

- **目的**：repo 大多是其他 AI 寫的，先評估品質，再建立實車程式的基礎。
- **評估發現**：
  - 模擬控制器 `line_follower.py` 有 4315 行、279 個寫死的常數、0 個 ROS 參數，靠模擬器的絕對座標做決策，**搬不到實車上**
  - 文件過期又互相矛盾，「目前狀態」分散在 5 個檔案；完全沒有自動測試
- **做法**：文件整理成 STATUS + real / sim / archive；新增 `wro2026_base_waverover`（底盤）、`wro2026_real`（bringup、URDF、line detector），寫了自動測試；最後請另一個 AI 獨立審查。
- **結果**：獨立審查找到 20 個問題，修了 17 個。**最重要的一個：`/cmd_vel` 收到 NaN 時，車子會用最高速前進**，現在一律當成停止。新加的測試在舊版程式上會失敗、新版會通過。
- **學到**：
  - **安全機制要能被測試證明**：逾時停車、限速、回授遺失停車、低電壓拒絕指令，每一項都有對應的測試
  - **AI 寫的程式要有獨立審查**：寫程式的 AI 自己檢查不容易發現 NaN 這種邊界情況
  - **控制器不能依賴模擬器才有的資訊**（例如真實座標），否則上實車就不能用

## 2026-10-12～13　WAVE ROVER 組裝與第一次控制

- **目的**：讓 Orin 能控制過渡用的測試車。
- **做法與結果**：
  - 裝 3 顆 18650（3 串），**第一次要插充電器才能開機**（保護板休眠）
  - 手機連車子的 Wi-Fi 熱點測試，四輪正常
  - Orin 用 HTTP 送 JSON 指令（`{"T":1,"L":..,"R":..}`）給 ESP32，寫了第一版 ROS 2 driver
  - 第一次自動測試：凌晨 Claude Code 在車子架空的狀態下自己跑完，全部 PASS
- **問題與判斷**：
  - 原廠配件（5 線杜邦線、Jetson Nano Adapter）是給 40-pin 外露的主機用的，Orin 的 40-pin 在金屬殼裡
  - 決定拆 Orin 前蓋，只接 3 條線：Orin pin 6（GND）、8（TX）、10（RX）。**5V 不接**，因為 Orin 和車子的 5V 都是輸出，接在一起會互相灌電
  - 車上的 5V 不能給 Orin 供電（Orin 要 9–20 V）
- **學到**：
  - **UART 的 TX / RX 要交叉接**：一邊的「送」接另一邊的「收」
  - **邏輯電壓要相同**：Orin 和 ESP32 都是 3.3 V
  - 沒有 encoder 的車，只能估方向，估不了走了多遠
- **未記錄**：原定 10-14 的 UART 接線測試，結果還沒記進來。

## 2026-10-11　Orin Nano 開機與環境建立

- **目的**：讓 Orin 能用、能遠端連、裝好 ROS 2。
- **做法與結果**：

  - `sudo` 問的是**登入密碼**，不是 Wi-Fi 密碼
